# Team Contract

## 5th Semester

**Project:** P5 - Complex Frontend & Backend Software  
**External Partner:** Metro Service A/S  
**Semester:** 5th Semester

**4 Scrum Teams**

---

## Project Overview

**Project:** Case C, Operational Restrictions (Driftsrestriktioner), a digital replacement for Metro Service's paper-based workflow

**Scope:** Authoring, multi-party approval and signing, operator read-and-sign, cancellation, a register of restrictions in force, automatic notification, and a five-year archive, usable remotely

**Context:** 5th Semester BSc Software Engineering, AAU Copenhagen, Autumn 2026

**Backlog:** 27 items across 12 epics, tracked as GitHub issues on the project board

## Responsibilities

All group members are expected to:

- Attend agreed meetings and Scrum events prepared.
- Honor agreements and deadlines.
- Actively contribute to the project.
- Communicate problems and delays as early as possible.
- Give and receive constructive feedback.
- Take responsibility for both their own work and the overall project result.

Each group is responsible for its own tasks but must collaborate when work or decisions affect other groups.

## Work Standards and Expectations

- **Branching:** `main` is protected and holds only what has been demonstrated at a review. `staging` is the integration branch and should always run. `development` is the shared working branch. Use one feature branch per backlog item, named for it (e.g., `MET-C-004-create-restriction`).
- **Before review:** Everyone makes a real effort on their work and finds out how things should be done correctly (e.g., by checking the documentation, existing ADRs, and the acceptance criteria) before sending it to review. Reviewers should not be the first to catch avoidable mistakes.
- **Pull requests:** At least 3 reviewers other than the author, and CI passing before merge.
- **Definition of Done:**
- **Interfaces:** Published interfaces other teams build against live in `contracts/` and are versioned. Breaking changes need advance notice to affected teams.
- **Decisions:** Significant architecture decisions are recorded as ADRs in `docs/adr/`.
- **Test data:** Only synthetic data in `fixtures/`. Never commit anything supplied by Metro, per the data handling guide.
- **README:** Must let a new developer clone and run the system. Test it by having someone from another team try it.
- **AI assistants:** We record which assistants we used and for what in the README (two lines suffice), following the semester AI-use policy. Every member must understand and be able to explain any AI-assisted code they submit.
- **Licence:** MIT, per Section 7 of the AAU and Metro Service collaboration framework.

## Scrum and Nexus

The four groups work as separate Scrum teams but collaborate as one unified project through Nexus.

We use:

- A shared Product Backlog.
- Joint Sprint Planning.
- Nexus Daily Scrum for coordination between groups.
- A joint Sprint Review.
- A joint Nexus Sprint Retrospective.
- A shared Definition of Done.

Relevant members from each group are appointed to coordinate dependencies and integration across the project. Work should be integrated continuously, and dependencies between groups should be communicated as early as possible.

**Success looks like:** Each sprint ends with something demonstrable at review, the README lets a stranger run the system, and every team member can explain the design decisions.

## Communication

**Primary Communication Channel:** Discord

Information that concerns multiple groups is communicated through a shared channel. Important decisions and changes must be documented so that all groups have access to the same information. Communication should be clear, respectful, and constructive.

## Meetings and Absence

All meetings and Scrum events are agreed upon jointly and are expected to be attended. In case of absence, notice should be given as early as possible to the relevant group. If an absence affects a deadline or another group's work, this must be communicated immediately.

### Meeting Conduct

- Phones are put away during meetings; they may only be used for tasks relevant to the meeting.
- Everyone arrives on time and prepared, having read relevant material (e.g., the backlog item, review comments, or agenda) beforehand.
- Everyone participates actively: questions are asked when something is unclear, and relevant input is shared.
- Laptops are only used for tasks relevant to the meeting (e.g., taking notes, demonstrating work, or looking up backlog items).
- Discussions stay on topic; longer side discussions are taken offline.

### Meeting Roles

For each meeting, the following roles are planned in advance where relevant:

- **Scrum Master:** One person plans and facilitates the meeting, keeps it on track and on time, and makes sure the agenda is covered.
- **Note taker:** One person takes notes of decisions, agreements, and action items, and shares them with the relevant group(s) afterwards.

The roles rotate between group members. Other roles (e.g., timekeeper or presenter) can be appointed as needed.

## Conflict Resolution

Problems should be addressed as early as possible, initially with the people involved. If the problem cannot be resolved, the relevant group members are involved, followed by the relevant members across the groups.

For major or persistent conflicts, the project supervisor may be involved. We focus on solving the problem rather than placing blame.

## Quality and Collaboration

All groups follow the shared Definition of Done and the agreed technical standards.

Work must be tested and able to be integrated with the rest of the project before it is considered complete. Technical decisions that affect multiple groups must be coordinated across the groups.

## Evaluation

The group contract is evaluated continuously through our retrospectives. If our way of working together is not effective, the contract can be changed by mutual agreement. At the end of the project, the contract is evaluated as a whole.

## Signatures

By signing, we accept the agreements outlined in the group contract and commit to contributing constructively to the project.
